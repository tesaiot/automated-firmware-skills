# Stage 3 - Layered code

```
main.c            application: wiring, command table, policies (what a button does)
  │ uses
func/*.c/.h       services: led (1-based, toggle, readback), button (debounce, events),
  │ uses           console (line editor + dispatch), later: sensors, storage, ipc...
board/board.c/.h  BSP adaptation: CYBSP_* aliases, Cy_* PDL calls, BOARD_xxx #ifdefs,
  │ uses           CM55 start, console UART access
bsps/<BSP>/       generated by configurators from design.modus (never hand-edited)
```

Rules
- Dependency direction is strictly downward. `func/` and `main.c` never include `cybsp.h`.
- A board difference is fixed in `board/` or in the BSP overlay - not with `#ifdef` in `func/`.
- Prefer BSP aliases (`CYBSP_USER_LED1`) over raw ports; tables shrink automatically when an
  alias is missing (`#if defined(CYBSP_USER_LED3_PORT)`), so the same code runs on boards with
  fewer LEDs/buttons.
- Active levels come from the BSP (`CYBSP_LED_STATE_ON`, `CYBSP_BTN_PRESSED`).
- ModusToolbox auto-discovers sources and include dirs under each project, so new folders
  need no Makefile change (avoid folder names starting with `COMPONENT_`, `TARGET_`,
  `TOOLCHAIN_`, `CONFIG_` unless intended).
- Board id reaches C as `-DBOARD_<ID>` (added by new_app.sh); `board.h` maps it to `BOARD_NAME`.

## Console protocol (test contract)

| Line | Meaning |
| --- | --- |
| `READY` | boot finished, accepting commands (printed after `INFO ...`) |
| `OK ...` | command succeeded, with resulting state (`OK led1=1`) |
| `ERR <reason>` | command rejected |
| `EVT ...` | asynchronous event (`EVT btn1=pressed led1=1`) |
| `<TAG> k=v ...` | state report (`LED led1=0 led2=1`, `BTN btn1=0`) |

Input: CR or LF terminates a line; characters are echoed. Keep lines < 64 chars.

## Adding a feature (recipe)

1. Need new hardware? Add the pin/peripheral in the BSP (design.modus) → alias `CYBSP_xxx`.
2. Add `board_xxx()` functions in `board/` hiding the PDL calls.
3. Add `func/xxx.c/.h` service with init/poll/get API (no blocking > 1 ms in poll).
4. Register console commands in `main.c`; print with the protocol above.
5. Add test steps to `tests/<app>.json` (automatic first, interactive only if a human is needed).

## Dual-core (CM33 NS + CM55)

Proven pattern (an earlier E84 `led-uart-ipc` demo, BSP 1.4.0): one core owns each peripheral.
- Hand over the debug UART: CM33 finishes printing (`Cy_SCB_UART_IsTxComplete`), disables and
  de-inits SCB, then starts CM55; CM33 must not printf afterwards.
- Mailbox in `m33_m55_shared` SOCMEM top 256 bytes, non-cacheable
  on CM55 (MPU), `NOLOAD` in the CM55 linker; order writes with `__DMB()` and sequence counters
  (`cmd_seq` / `ack_seq`). Don't touch the BSP's mtb-ipc/SRF channel 0, its semaphores or
  `MTB_IPC_IRQ_USER..+3`. Put shared headers in `<app>/shared/` with `INCLUDES+=../shared`.
- The address depends on the BSP memory map - re-derive it per board from `cycfg_memory.h`.
- Template `dual-core-ipc` packages this with the roles swapped (CM33 keeps the console so the
  standard serial tests apply; CM55 executes mailbox requests and drives LED1/LED2; CM33 reads
  the pins back). Built 0-warning on an E84 board 2026-10-04; not yet run on KIT_PSE84_AI hardware. To give CM55
  the UART instead, use the hand-over above and a CM55-side test spec.
